# ACL evaluation order, and why a read ACL on a field silently wins

*2026-09-18 22:03 UTC*

ACL evaluation is not additive across specificity levels — it's "most specific match replaces the general one," not "table ACL AND field ACL." For a given operation (read, write, create, delete) on a given field, the engine looks for a `table.field` ACL first. If one exists, it evaluates *only* that ACL for that field. The table-level `table.none`/wildcard read ACL is skipped entirely, roles and all.

This is where people get burned. Someone locks down `incident` read access behind `itil`, feels done, then later adds a field ACL on `priority` for an HRSD integration without re-adding the role check:

```
Table: incident
Type: read
Field: priority
Role: (none)
Script: (none)
```

Now `priority` is readable by anyone with plain access to the incident record — the table-level `itil` requirement never gets consulted for that field. No error, no log entry, just quietly broader exposure than intended.

Multiple ACLs at the *same* specificity level do get ANDed (all must pass, unless `security_admin` is elevated and one ACL is scoped to bypass). But specificity beats generality outright. When auditing security, don't just check the table ACL and assume it cascades — pull every ACL row where `table = 'incident'` and inspect field-scoped entries independently; they're evaluated in isolation, not in addition.
