# The `sys_id` as a foreign key: reference qualifiers under load

*2026-09-27 22:41 UTC*

The reference qualifier on a reference field isn't evaluated once when the form loads. If it's a script-based (advanced) qualifier, it runs on every keystroke in that field's autocomplete, via `ReferenceAJAXProcessor`. A simple encoded-query qualifier gets cached client-side after the first fetch; a script qualifier does not, because the platform can't know in advance whether the script's output depends on other field values on the form. That distinction is the part people miss — they write a "smart" filter, test it once, see it work fine, and never notice it's re-querying the database per character typed by every user with that form open.

The failure mode shows up as CPU spikes on nodes serving forms with a reference field that has a busy autocomplete, not as slow page loads. A qualifier like this looks harmless:

```javascript
// Advanced reference qualifier on 'assignment_group' field
answer = 'active=true^manager=' + current.variables.request_manager +
         '^ORDERBYname';
```

If `request_manager` triggers a dot-walk that isn't in the base table's index, every keystroke pays that cost. Multiply by concurrent users on a busy form and you get transaction queue backups that look unrelated to the field itself.

Fix pattern: push the filtering logic into a script include function called via `javascript:new MyQualifier().getGroups(current)`, keep the underlying query index-friendly, and if the qualifier doesn't actually depend on other form fields, use a plain encoded query instead of a script — so the client can cache it.
