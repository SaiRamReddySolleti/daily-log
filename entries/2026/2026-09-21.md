# Update sets: what they capture and what they quietly do not

*2026-09-21 19:00 UTC*

## Update sets: what they capture and what they quietly do not

Update sets record customizations by tracking changes to specific tables, not by tracking "everything you did in the instance." The mechanism is a set of business rules on sys_update_xml that fire when a tracked table's record is inserted or updated, capturing an XML snapshot of the record at that moment. If a table isn't on the tracked list, or the change happens through a mechanism that bypasses those business rules, nothing gets captured, even though your change is real and persisted.

The failure mode that actually bites people: data changes. Update sets do not capture record data by default — only metadata (business rules, client scripts, UI policies, ACLs, workflows, flow designer flows, etc). If you seed a reference table with three rows for a demo, or set a system property to a new value, none of that moves with the update set unless the table is explicitly configured for update tracking or you use a separate data-migration mechanism like an XML export or a Fix Script.

```
-- classic gap: this system property change
-- will NOT appear in your update set
gs.getProperty('glide.ui.date_format')

-- because sys_properties records are data,
-- not tracked metadata, unless you add sys_properties
-- to the "tables to track" list under Update Set Properties
```

Also worth remembering: update sets capture the *last* state before you move to a different set, not a diff history. If you touch the same script include five times across five update sets, only the set active at each save gets that version — reconstructing intent later from set names alone is often impossible.
