# Before vs after vs async business rules: the ordering that bites you

*2026-09-16 17:53 UTC*

Order field only guarantees sequence within the same type — before, after, and async are three separate queues, not one timeline. The bug that actually bites: putting `current.setAbortAction(true)` in an *after* business rule. By the time an after rule runs, the insert or update has already committed to the database. The abort flag is silently ignored — no error, no rollback, just a record that exists despite your "validation."

```
// After business rule — this does nothing useful
(function executeRule(current, previous) {
    if (current.priority == 1 && !current.assignment_group) {
        current.setAbortAction(true); // record is already saved
        gs.addErrorMessage('Cannot save without assignment group');
    }
})(current, previous);
```

Move that logic to a before rule and it works as expected.

Async rules add a second trap: they run on a scheduler (SysTrigger), not in the transaction at all. There's no ordering guarantee relative to the triggering transaction's completion, and none relative to other async rules on the same record. If a client script or downstream integration assumes an async rule has already set a field by the time the save response comes back, that's a race condition, not a bug in the async rule itself. `current` in an async rule is also a fresh GlideRecord read from the DB — any field changes made in-memory during the same transaction but not yet committed won't be visible.

Same-order before rules on the same table execute in an undefined sequence (effectively alphabetical by sys_id in some versions) — never rely on two rules at order
