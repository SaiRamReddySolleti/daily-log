# `GlideRecordSecure` vs `GlideRecord`: what "secure" covers

*2026-09-19 16:57 UTC*

`GlideRecordSecure` is `GlideRecord` with ACL enforcement forced on, even in contexts that normally bypass it — background scripts, global business rules, script includes not flagged for scoped security. Regular `GlideRecord` in those contexts runs as the system user for query performance reasons; ACLs on the table still apply to client-facing access, but a server-side script using plain `GlideRecord` will happily return or write fields a real user couldn't touch.

The part people get wrong isn't read enforcement, it's write enforcement. `GlideRecordSecure` doesn't throw when a field-level write ACL fails — it silently skips that field and reports success on the rest of the update.

```javascript
var gr = new GlideRecordSecure('incident');
gr.get(sysId);
gr.setValue('priority', 1);       // blocked by a write ACL, say
gr.setValue('short_description', 'updated via script');
gr.update();                      // returns true

gs.info(gr.priority + '');        // still the old value, no error thrown
```

If you're validating "can this user actually make this change" logic, check `gr.canWrite('priority')` before assuming the write took.
