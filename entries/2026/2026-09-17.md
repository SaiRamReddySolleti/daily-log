# Display business rules and the `g_scratchpad` round trip

*2026-09-17 17:52 UTC*

A display business rule runs server-side before the form renders, and whatever you attach to `g_scratchpad` gets serialized into the page's initial HTML as a JSON blob. That's the part people miss: it's not a live channel to the server, it's a one-time snapshot taken at render. If you set `g_scratchpad.foo` in a display BR and then expect a later async BR or an ACL check to update it, nothing happens — the client already has its copy and the server object is gone once the page is built.

The failure mode I actually hit: two display business rules on the same table, both writing to `g_scratchpad`, but one of them does a flat reassignment instead of adding a property.

```javascript
// Display BR #1, order 100
g_scratchpad.slaBreached = current.sla_due < new GlideDateTime();

// Display BR #2, order 200
g_scratchpad = {};              // wipes out slaBreached from BR #1
g_scratchpad.vipCaller = current.caller.vip;
```

Because business rule order determines execution sequence, BR #2 silently nukes whatever BR #1 set. The fix is trivial — always do `g_scratchpad.vipCaller = ...` and never reassign the object — but it's invisible until a client script downstream reads `g_scratchpad.slaBreached` and gets `undefined`, and the bug only shows up depending on which BR happens to run last.

Also worth remembering: only JSON-serializable primitives survive the trip. Passing a `GlideRecord` or raw `GlideDateTime` object into scratchpad just gives you a broken object client-side; convert to string first.
