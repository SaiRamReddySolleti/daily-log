# Scoped apps and cross-scope privileges

*2026-09-20 17:12 UTC*

Cross-scope access is gated before ACLs ever run, and that ordering trips up people who try to fix a scope violation by loosening a Read/Write ACL. The platform checks the target artifact's "Accessible from" property and any matching `sys_scope_privilege` record first. If that check fails, you get an application scope violation, not an ACL denial — the two errors look similar in the logs but come from completely different layers.

The default direction of "Accessible from" is backwards from what most people assume. Tables default to "all application scopes" (readable/writable across scopes once ACLs allow it). Script Includes default to "this application scope only." So a scoped CSM app calling a global Script Include will fail even if the Script Include is marked client-callable and the user has every role in the world.

Fixing it means either flipping the Script Include to "all application scopes" (rare, usually wrong) or creating an explicit privilege grant:

```
sys_scope_privilege:
  target: global.MyUtilityScriptInclude
  type: script_include
  operation: execute
  status: allowed
```

New privilege records land as "not requested"/pending until an admin approves them, so a common failure mode in dev-to-test promotion is the update set moving cleanly but the privilege record staying unapproved in the target instance, silently breaking the integration until someone checks System Applications > Cross Scope Access.
